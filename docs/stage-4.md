# Stage 4 — Usage records

- Every tool call (MCP over HTTP, console, stdio when USAGE_DB is set) goes through `invokeTool`, which logs: time, caller, source, tool, args (≤2 KB), duration, ok/error → SQLite `data/usage.sqlite` (`tool_calls`).
- Caller identity: console → logged-in email; MCP over HTTP → owner of the personal `aimcp_` token (the shared access token is rejected on /mcp since 2026-11-12, so every call has a person); stdio → FEEDMOB_USER_EMAIL.
- Personal tokens: generated in the console ("我的 MCP 令牌"), shown once, stored as SHA-256 hash, revocable.
- `get_usage_stats` MCP tool + console page: totals, failure rate, by tool / person / day / source, filterable call list.
- `TALLY_AUTH_MODE=local` retains self-declared email and shared-token login solely for isolated development. The HTTP process requires an explicit mode; do not expose local mode to a team.
- `TALLY_AUTH_MODE=google` requires a Google OAuth web client and an HTTPS callback at `/auth/google/callback`; `GOOGLE_CLIENT_ID`, `GOOGLE_CLIENT_SECRET`, and `GOOGLE_CALLBACK_URL` must be configured before startup. The HTTPS origin must match the public origin and terminate at a trusted reverse proxy. Configure the exact redirect in Google separately; no external configuration or deployment is done by the code.
- Team login uses authorization code with PKCE, browser-bound one-use state and nonce, Google library signature/issuer/audience verification, strict expiration and verified email plus `hd=feedmob.com`. Identity used for dashboard audit is the provider-returned email. Credentials and identity tokens are not stored in session or logged. Sessions and login transactions are in memory and are lost on restart; multi-instance operation requires shared state or sticky routing.
- Configure the trusted proxy and its observability to omit callback query strings and authorization headers from access logs; the callback contains a one-use authorization code. Ensure direct backend access is restricted to the proxy. Production Google consent, callback registration, TLS termination, secret storage, and an actual provider login are not configured or validated here.
- The SQLite migration adds nullable issuer and subject fields without assigning ownership to old tokens. In Google mode, only tokens issued from a verified Workspace session are accepted; legacy tokens remain in the database and keep working in isolated local mode, but are rejected in Google mode with a reissue hint. Users must sign in through Google and issue new tokens; no legacy token is automatically claimed or revoked. Back up the usage database before upgrading; the migration is repeatable.
- Team token ownership, listing and revocation use the validated issuer and stable Google `sub`, not email. The stored email is the verified provider email at issuance and is used as the readable MCP audit caller; it may become stale after a rename. Dashboard audits use the verified email from the current login. Local mode can manage only unverified local tokens.
- Google claims, source account lifecycle and session revocation in the provider are not continuously rechecked during a 12-hour session or for existing personal MCP tokens. Plan administrative revocation and lifecycle controls before team rollout. Explicitly select the authentication mode on upgrade and validate team login in Staging with an authorized Google OAuth client before use.
